# Issue Buddy planning: forbid builds and installs in the planning worktree and define who formats the plan

**Plan status:** Implemented
**Source:** effective-flow plan
**Recommended workflow:** Feature (`effective-flow build`)
**Issue:** #800

## Requirement

Issue Buddy's Phase 4 planning sub-run may write exactly one new untracked plan file in the pass's `issue-planning` worktree (`PLANNING_ROOT`). Two gaps in the shipped contract make that boundary fail in practice:

- The separate brief that `src/tools/issue-buddy.md` hands the sub-run does not forbid build, install, test or generated-output commands. A sub-run that ran `node build.mjs` there created several hundred ignored files under `dist/`. The parent's snapshot comparison already counts ignored entries, so the pass stopped, but the boundary is only enforced after the fact.
- `src/shared/unattended-planning.md` "Completion" tells every unattended entry to "finish formatting". A fresh planning worktree has no installed dependencies, and the sub-run may not install any. The contract does not say what happens then, and nobody else formats the plan before Issue Buddy publishes it. An unformatted plan then fails `pnpm agent:check` (oxfmt `--check` over the whole repository, `docs/plan/**` included) on the plan pull request and on later delivery commits.
- A related template gap: nested items under `- [ ]` checklist items written with six-space continuation are restructured by the formatter. The plan contract gives no formatter-stable form.

Goal: the brief states the prohibition up front for the sub-run and every agent it starts, the parent's mutation check names new ignored and untracked paths, every unattended `DONE` entry has a defined formatter-unavailable branch, the Issue Buddy parent formats the plan before publication or stops the pass before planning, and the plan contract documents a nested checklist form that the formatter keeps.

Workflow rationale: Feature (`effective-flow build`). The change adds a formatter preflight, a new parent step (formatting before publication with a second `publication-metadata` call), a new completion branch and a new contract rule, each with tests. Archived plans for comparable Issue Buddy contract changes are also routed as Feature.

## Architecture decisions

- **The parent is the only formatter in an Issue Buddy pass.** The separate brief forbids the sub-run every project tool in `PLANNING_ROOT`, the formatter included, and requires it to carry that prohibition into every agent it starts (codebase examination, judgment, scoring and review leaves). In an Issue Buddy pass the sub-run therefore always takes the formatter-unavailable branch of "Completion", and the parent always formats before publication. Rationale: the sub-run cannot install under its one-file write boundary, a formatter run there may write caches that the parent's mutation check counts as a stop, and in a pass with several issues the sub-run for a later issue would otherwise see whatever state an earlier step left behind.
- **One formatting rule per path.** For every unattended `DONE` entry (`plan`, the `plan-review` file delegation, the `plan-review` autopilot file review), `src/shared/unattended-planning.md` "Completion" formats only when the formatter can be called directly as an already-present binary, scoped to the plan file, changing no other path, unless the caller's brief forbids project tools. It never runs through a package manager, `pnpm exec`, `npx` or a runner, and never downloads. Otherwise the plan stays unformatted and `Notes:` carries `formatter: unavailable`. This replaces today's unconditional "finish formatting" for those entries as well. `src/tools/plan.md` Phase 7 step 2 also runs on the unattended path, so it gains one clause handing unattended runs to that rule; it keeps no second copy.
- **What counts as a direct call.** The formatter is the executable that the project's instructions name: a package script whose command is a single executable resolves to that executable with the plan path appended, and a package-manager-generated bin shim (such as `node_modules/.bin/<name>`) is a direct call. "Cannot be scoped to one file" means the executable itself accepts no path argument, not that the script lacks one.
- **Formatter availability is a preflight (scored decision, see "Decided by score").** Once per publishing pass, right after `PLANNING_ROOT` is created and the caller contract's `consent-check` has passed in Phase 2, and before recovery, judgment or planning, the parent resolves whether the project's instructions name a Markdown formatter. If one is named, it checks that the formatter can run directly as defined above, with working directory `PLANNING_ROOT`, as host instructions allow. A named formatter that cannot run stops the pass with stage `format`, code `FORMATTER_UNAVAILABLE`. That stop needs no plan preservation and leaves no planning worktree behind, because nothing has been planned yet.
- **Runner-only hosts stop at the preflight (scored decision).** If host instructions allow project tools only through a runner, the formatter cannot run directly and the preflight stops every publishing pass, including autopilot runs from issues. The user guide names the operator remedy: an installed formatter that host instructions allow to be called directly.
- **The parent validates, formats, then validates again.** The first `publication-metadata` call keeps today's issue-failure mapping for structurally invalid plans before any formatting. The formatting step touches only the plan file. A second `publication-metadata` call must return the same `planFile`, `reviewResult` and `openPointCount`, and its projection is the retained one. `<metadata blobOid>` is defined once in Phase 4 as that retained blob, so the Phase 5 `expectedBlobOid` and the `issue-buddy-base-move` re-run both bind the formatted bytes.
- **Creation identity survives the parent's own format.** The recorded creation identity of the plan is its file type, device, inode and a link count of 1, never its modification time or size. If the parent's format replaced the inode (a formatter that writes through a temporary file and rename), the parent re-records the creation identity from the formatted file, but only after the second `publication-metadata` call succeeds on it. Phase 5's protected removal then uses the retained identity and the formatted blob. The parent's own format is not an "overwrite" in the Phase 4 sense.
- **The parent never installs (scored decision).** It uses only an already-installed formatter that the project's instructions name, taken from the primary checkout at `RUNTIME_STATE_ROOT`. It runs that formatter directly on the plan path with working directory `PLANNING_ROOT`, so `PLANNING_ROOT`'s formatter configuration applies. There is no install, no lifecycle script and no download under the credential-holding parent. Accepted residual trust: the parent still executes that installed third-party binary, the same one the operator runs locally.
- **No configuration row; a project without a named formatter publishes as-is (scored decisions).** A named formatter that cannot run stops the pass at the preflight. If the project names no Markdown formatter at all, the parent publishes the plan as-is and states this in its Phase 6 chat report. This departs from proposal item 3, which allowed unformatted publication only under a configuration row. A repository with a formatter check fails CI on an unformatted plan anyway, and a repository without one would otherwise stop every pass on the same issue.
- **The formatter is discovered, never hard-coded.** The parent takes the formatter command from the project's instructions (`AGENTS.md` and its includes, package scripts, formatter configuration files, host instructions). Ambiguous instructions count as a named formatter that cannot run. The tool source names no runner, package manager or formatter.
- **The parent never reads plan prose.** The formatting step keeps the formatter's stdout and stderr out of the parent's context and evaluates only the exit status. A stop's persisted `pass-report` entry stays exactly `{issue: null, stage, code}`. Its safe details go only into the Phase 6 chat report: the formatter executable's name, the repository-relative plan path and the exit status, with no absolute host path.
- **Formatter-stable checklist form in the plan contract.** `src/shared/plan-contract.md` owns plan artifact form, so it gets the nested checklist rule. Nested items and continuation lines under a `- [ ]` item start at the parent item's content column, which is two spaces. The rule comes with one minimal example. The flat template lines in `src/tools/plan.md` and `src/tools/plan-issue.md` stay unchanged.
- **Formatter stability is proven by `agent:check` (scored decision).** A committed fixture under `test/fixtures/` holds the documented nested checklist form, and CI's `pnpm agent:check` checks it. A node:test case pins the fixture's block to the example in `plan-contract.md`. `pnpm test` gains no formatter dependency.
- **`plan-lint` stays structural.** `publication-metadata` (`src/scripts/plan-lint-core.mjs`, `publicationMetadata`) neither runs nor emulates a formatter.

### Edge cases

- **Formatter already installed in `PLANNING_ROOT`.** This cannot happen in a fresh worktree, and the parent never installs there. If it does, the sub-run still does not format (the brief forbids it), and the parent formats as usual with the binary from `RUNTIME_STATE_ROOT`.
- **Formatter output is already formatted.** The second call returns the same `blobOid` as the first; publication proceeds.
- **Formatter rewrites through a temporary file and rename.** The inode changes; the parent re-records the identity after the second call succeeds. A leftover temporary file or a cache is a new path: `FORMAT_FAILED`, plan preserved.
- **This repository's own formatter.** `pnpm format` is the script `oxfmt` without a path; it resolves to the single executable `oxfmt`, called through `RUNTIME_STATE_ROOT`'s `node_modules/.bin/oxfmt` shim with the plan path appended.
- **Executable that accepts no path argument.** It cannot be scoped to the plan file: `FORMATTER_UNAVAILABLE` at the preflight.
- **Host instructions allow project tools only through a runner.** The formatter cannot run directly: `FORMATTER_UNAVAILABLE` at the preflight on every publishing pass, autopilot from issues included. The user guide names the remedy.
- **Installed formatter version differs from `PLANNING_ROOT`'s lockfile.** Residual risk: the plan may still fail `agent:check`. CI catches it on the plan pull request; this plan does not claim to prevent it.
- **Formatter output quoting plan text.** It is discarded; the parent evaluates only the exit status.
- **Base move after formatting.** `issue-buddy-base-move` compares against the retained post-format projection, so a formatted plan does not trip `BLOB_CHANGED`.
- **Dry-run passes.** The preflight and Phase 4 run in publishing mode only, so dry runs neither preflight, plan nor format.
- **Other unattended callers** (autopilot through `plan` or `plan-review` without Issue Buddy). Their "finish formatting" becomes the direct-call rule: they format only through an already-present executable and otherwise report `formatter: unavailable`. Their later formatting stays with their implementing workflow and is out of scope.
- **Ordered or other nested lists in plans.** The contract rule covers `- [ ]` items. It states the content-column principle once, and other lists follow the formatter's usual indentation.
