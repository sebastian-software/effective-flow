# Protected macOS validation for exact current content

**Plan status:** Implemented
**Source:** effective-flow plan

A trusted operator outside the closed worker exports exact current product content, submits an approved GitHub-hosted macOS workflow, verifies actual Actions backend evidence, and publishes a result into a mailbox the worker can read but cannot alter. The same waiting validator reads that result, judges the current content, and emits its normal gate evidence. This is new orchestration behavior, hence Feature.

## Architecture decisions

- Keep authority outside the worker. The worker can request validation and read a result; it receives no GitHub credential, private signing key, observer original, operator process control, deployment permission, or model/provider credential. Digests establish identity only.
- Use an explicit trusted-host bootstrap and an OS-protected result mailbox. Before a closed worker starts, the trusted host fixes the physical mailbox root and policy identity in its immutable launch input, protects that root from worker and descendant writes, and proves actual denial with canaries. Operator private/auth state is separately inaccessible for reads. A worker-created path, caller boolean, copied host receipt, or recomputed digest cannot establish this trust. A trusted host sidecar starts before synchronous launch and publishes per-validator admission only after observing the actual session chain. Until admission exists, its read-only wait stays pending; missing protection or contradictory admission refuses the lane.
- Extend the build-run helper with three distinct operations: read-only `validation-await-admission`, append-only `validation-request`, and read-only `validation-result`. The original validator polls in its existing task, or waits through a bounded process; no user question, human reply, new model thread, or replacement agent mediates completion. A verified remote result remains execution evidence, never the validator's judgment.
- Preserve the existing gate names, full commands, normal review and final-validation phases, correction limits, native evidence grammar, and terminal acceptance checks. The immutable original `create.remoteValidation` descriptor fixes `{protocol, requiredGates, policyDigest}` and makes each selected remote gate mandatory even before bootstrap admission or a validation request exists. That gate stays blocked until its current matching backend evidence is verified; plain `retain-evidence`, `receipt`, or user reply cannot discharge it.
- Separate the immutable source projection from the complete local build-run snapshot. Bind HEAD, index, tracked bytes and modes, relevant untracked bytes, exact export manifest, immutable remote commit/tree, approved workflow bytes, and command/environment policy. The operator rechecks local content during export and result publication, and the helper rechecks it on every result read and gate receipt.
- Use a dedicated, bounded snapshot branch `effective-flow/validation/<request-id>` with a `push` trigger. Include only the approved workflow at an active workflow path on that branch; transport every other original workflow as inert hash-bound payload and restore it only after job launch inside a separate faithful test workspace. Do not activate unrelated release/deployment workflows. This can run before the draft PRs merge. Planning performs no branch push or workflow execution. The already authorized model-free qualification creates one unique immutable branch per qualification request and inspects its actual Actions backend evidence. Changed source HEAD, index, product tree, workflows or execution closure requires a fresh request and a new create-only branch; never reuse the old proof, update its branch or treat an Actions rerun as current-content acceptance. Initial dirty-source qualification and later final committed-source qualification may both be necessary. They are model-free validation jobs, remain within the authorized Actions scope, and all jobs/resources must be accounted; neither starts a model or pilot attempt004.
- Keep the execution workflow and trusted operator small and dependency-free. The external operator may use the existing authenticated GitHub CLI outside the sandbox; the shipped worker helper has no GitHub transport or authentication dependency. No new dependencies, configuration keys, ADRs, installs on the maintenance host, or release/version changes.

### Component structure and interface seam

The immutable original `create.remoteValidation` descriptor is `{protocol, requiredGates, policyDigest}`. It establishes the remote requirement before any validator or admission exists. For those gates, missing admission/request/result cannot make a plain gate receipt valid. A worker cannot downgrade or omit this descriptor on a later call, nor use pending admission as permission to run a weaker local substitute.

`validation-await-admission` accepts the normal common fields plus `validatorHandle` and `gate`. It returns bounded `pending` or the exact trusted `bootstrapRef`. It reads the fixed protected mailbox only and creates no product, control or result records, acquires no operation/lifecycle/pilot lock, grants no authority, and triggers no model or human reply. The same validator invokes it before `validation-request`; no request needs to exist to discover admission.

The trusted host starts `protected-validation-host.mjs` as a sidecar before the synchronous closed-worker launch. The sidecar observes protected native session metadata and canonical successful `create`/`bind-agent` helper events to correlate the actual root, bound build runner and validator. It verifies the original remote descriptor, exact policy and observed session ancestry before exclusively publishing admission. Do not assume a `receiverThreadIds` field or accept caller-supplied parent/role relationships. Pending metadata remains pending; missing, contradictory or foreign observations fail closed. This resolves the synchronous-launch deadlock without another model turn or user-reply channel.

`validation-request` uses the normal common fields `{runtimeStateRoot, repositoryIdentity, runId, requestDigest}` plus a unique validation ID, actual validator handle, required gate (`validation` or `final-validation`), and the trusted bootstrap reference. Its immutable record adds the current complete snapshot, retained export manifest, approved policy digest, exact command list, mandatory native-case names, environment identity, request time and unique nonce. Only one outstanding request for the same validator/gate/content may exist; duplicate or conflicting creation refuses rather than overwriting. Normal bounded Quality correction preserves earlier failed/stale requests append-only and creates a fresh current-content request. Historical successful request creation alone is not replay. The final gate receipt selects exactly its current request/result chain; prior non-consuming failed/stale chains remain separately checked and retained, without replacing current acceptance or blocking that valid correction. Replay, session substitution, duplicate consumption and changed-content proof reuse remain refusals. The build runner and validator remain separately identified. Bind the actual validator handle through the existing trusted host worker-dispatch channel, not a caller claim of independence.

`validation-result` accepts only common fields, exact request reference, and the same validator handle. It selects the result beneath the bootstrap's fixed physical protected mailbox; it never accepts an arbitrary success object, operator path, trusted flag or replacement trust anchor. It returns a bounded `pending`, `failed` or `verified` projection and evidence references. Missing/incomplete evidence stays pending or fails with a stable diagnostic; malformed/foreign evidence fails closed. Polling reads no credentials, mutates no product or protected result state, and holds no operation/lifecycle/pilot lock while waiting. It performs a fresh content comparison even for an already verified result.

The normal gate `receipt` requires the verified request/result references for every gate selected by the immutable original remote descriptor, including when bootstrap or request is still absent. It also verifies outstanding remote requests for that gate. It verifies their binding and current content again and records the validator's real judgment once. A result cannot complete both gates or be transplanted to another validator/run. The result operation itself never records a passed gate. Preserve existing callers and gate behavior when the original create descriptor selected no remote lane; do not silently change normal builds into remote builds.

The operator owns the protected bootstrap, append-only result publication and actual GitHub API transport. Its test seam injects backend responses and process/file observations, not `success:true` or a trusted-result bypass. Preparation returns a bounded receipt and local manifest. Submission binds the exact prepared commit/branch once. Observation binds the returned actual run ID and attempt, fetches backend metadata/logs itself, and writes the terminal result exclusively. Unknown submission outcomes require reconciliation against that same immutable intent, not a new push/run. A new Actions attempt requires a fresh explicitly bound observation; evidence from different attempts cannot be combined.

The shared protocol exposes one JSON shape per boundary, with unknown keys rejected. The exact shared contracts are:

A negative test must show that substituting a worker-created bootstrap/mailbox is rejected. If this binding cannot be implemented with the existing native host seam, stop remote qualification and report the precise missing proof; do not ship an accepted-but-unprotected mode.

### Edge cases

- Content, index, source branch, workflow, environment pin or relevant untracked drift invalidates the result, even if HEAD is unchanged. Preserve failed request evidence and require the validator's normal correction path.
- Unknown keys, malformed UTF-8/JSON, oversize controls, unsafe file identity, symlink swaps, foreign repository/run/validator/gate/nonce, duplicate result, stale content and replay refuse without repair or overwrite.
- Missing/truncated logs, pagination gaps, absent job/step/case, cancelled/timed-out/failed/skipped execution and contradictory backend metadata never verify. Expected native cases cannot be replaced with reduced suites.
- Concurrent publication, uncertain network completion and Actions reruns retain identities and evidence. No implicit retry, merged attempt logs, force push or repeated side effect.
- Operator unavailability and bounded polling timeout leave the same validator and gate pending or return an honest blocked result. No worker network exception, host test substitution or fabricated user answer is permitted.
